    Publishing on OperatorHub¶

    How the operator is packaged for Operator Lifecycle Manager (OLM) and listed on OperatorHub. This is milestone 3 item D2 (see REQUIREMENTS.md section 14). The catalog rules below were checked against the community-operators and operator-pipelines docs on 2026-11-01; check them again before each first-of-its-kind submission, because both repositories change their process from time to time.

    1. Where the operator gets listed¶

    Catalog Repository Seen in Tested by their CI on
    OperatorHub.io (upstream Kubernetes) k8s-operatorhub/community-operators operatorhub.io, the quay.io/operatorhubio/catalog index, Artifact Hub kind/minikube
    OpenShift and OKD embedded OperatorHub redhat-openshift-ecosystem/community-operators-prod the OpenShift console, registry.redhat.io/redhat/community-operator-index:v4.x an OpenShift 4 cluster

    The two catalogs are separate, with one pull request to each for every release. A listing on OperatorHub.io does not show up on OpenShift. The certified and Red Hat Marketplace catalogs are a different programme and out of scope.

    Order: OperatorHub.io first (its CI matches what we test on), then OpenShift once a release has run on a real OpenShift cluster.

    2. How the bundle is built¶

    operator-sdk is used as a build tool only; the operator has no SDK code. make operator-sdk downloads the pinned release into bin/.

    Path What it is
    config/manifests/bases/harbor-resource-operator.clusterserviceversion.yaml CSV base: tile text, description, icon, keywords, links, maintainers, install modes, minKubeVersion, capability level. Written by hand; operator-sdk generate kustomize manifests keeps it and only refreshes the owned CRD list.
    config/manifests/kustomization.yaml Input for make bundle: config/default, the samples and the scorecard config.
    config/manifests/samples/ config/samples with the Secrets removed. The bundle must not ship credentials, and alm-examples only lists custom resources. The CSV description names the Secrets users create.
    config/scorecard/ Scorecard tests (basic and OLM suites).
    docs/images/icon.svg The project's own icon, embedded in the CSV. It is not the Harbor logo.
    bundle/, bundle.Dockerfile Generated by make bundle; committed for each release, and copied as-is into the catalog repositories.

    Targets:

    make bundle            # regenerate bundle/ for VERSION (channel alpha) and run the basic validation
make bundle-validate   # the checks OperatorHub runs (suite=operatorframework)
make bundle-build      # bundle image BUNDLE_IMG (default ghcr.io/oreondev/harbor-resource-operator-bundle:vVERSION)
make bundle-push

    USE_IMAGE_DIGESTS=true make bundle pins the manager image by digest and fills spec.relatedImages, which disconnected OpenShift clusters need. It is off for now, so the CSV says features.operators.openshift.io/disconnected: "false".

    On a vX.Y.Z tag the release workflow checks that the committed bundle/ is for X.Y.Z, runs make bundle-validate, pushes and signs the bundle image, and attaches harbor-resource-operator-bundle-X.Y.Z.tgz to the GitHub release.

    Validation result¶

    make bundle-validate passes. It prints one warning, which is a false positive: the events.k8s.io events rule in the CSV is reported as "deprecated and removed in v1.25". What was removed in 1.25 is events.k8s.io/v1beta1; the operator uses events.k8s.io/v1, but RBAC rules carry no API version, so the validator flags the group. Removing the rule would break event recording.

    3. CSV choices¶

    Field Value Why
    capabilities Seamless Upgrades (level 2) REQUIREMENTS D2. The CRDs are v1alpha1 with additive changes only, which OLM upgrades cleanly. Level 3 ("Full Lifecycle", backup and restore) does not fit an operator that does not run Harbor. Level 4 becomes possible once a PrometheusRule and a dashboard ship in the bundle. An upgrade test (section 6) should back the level-2 claim from the second release on.
    categories Integration & Delivery, Developer Tools from the catalog's categories.json
    installModes AllNamespaces only the operator's default. OwnNamespace/SingleNamespace/MultiNamespace would need --watch-namespaces fed from the OperatorGroup annotation olm.targetNamespaces, plus a test.
    minKubeVersion 1.30.0 the oldest version the end-to-end suite runs on (nightly on a kindest/node:v1.30 cluster). It was 1.34.0 up to 0.1.3, which failed the OperatorHub.io kiwi test: that job runs kind with Kubernetes 1.30, so OLM never created the Deployment. Lower it only together with the nightly job
    maturity, channel alpha, default channel alpha add a stable channel when the API reaches v1beta1 or v1
    provider Oreon IT, https://www.oreonit.com the company that maintains the project. The listing shows the name as plain text and does not link provider.url, so the site is also in links
    maintainers Fahri Cap, fahri.cap@oreonit.com
    links, support GitHub repository, README, issues, the Harbor Helm chart, Oreon IT there is no separate docs site yet; switch Documentation when there is
    arch labels amd64, arm64, ppc64le, s390x, linux the release image is built for these
    OpenShift feature annotations proxy-aware: "true", everything else "false" the Harbor transport clones Go's default transport, so it reads HTTPS_PROXY/NO_PROXY; confirm once on a proxied cluster

    Descriptors and resources come from // +operator-sdk:csv:customresourcedefinitions:... markers in api/v1alpha1: one on each kind (display name and the resources it uses) and one on each top-level spec field and on status.conditions. Add the marker when adding a spec field, or the scorecard's olm-spec-descriptors test fails. The kind marker must stay inside the +kubebuilder marker block; a blank line between them makes controller-gen drop the short names, printer columns and status subresource.

    4. Before the first submission¶

    1. Make the bundle image public. After the first release that pushes it, set harbor-resource-operator-bundle on ghcr.io to public, like the operator image and the chart. The catalog CI pulls the manager image anonymously; the bundle image is only for our own tests and operator-sdk run bundle.
    2. Install test with OLM on kind. Install OLM (operator-sdk olm install), build and push a bundle image somewhere the cluster can pull from, then operator-sdk run bundle <bundle image> --namespace operators. Check that the CSV reaches Succeeded, the manager Deployment is available, and a HarborConnection to a real Harbor becomes Ready. Then run operator-sdk scorecard <bundle image>; the basic and OLM suites must all pass. Clean up with operator-sdk cleanup harbor-resource-operator. This catches RBAC that works with kustomize but is missing from the CSV.
    3. Version. v0.1.0 was released before the bundle existed, so it has no bundle image or archive. The first submission is 0.1.2, the first release with the final provider listing (0.1.1 had a placeholder provider).

    5. Submitting a release to OperatorHub.io¶

    1. Fork k8s-operatorhub/community-operators and branch from its main.
    2. Copy the release's bundle into the fork: 
      mkdir -p operators/harbor-resource-operator/X.Y.Z
cp -r bundle/manifests bundle/metadata operators/harbor-resource-operator/X.Y.Z/
      (or unpack harbor-resource-operator-bundle-X.Y.Z.tgz from the GitHub release). The tests/scorecard directory is optional; leave it out.
    3. The first time only, add operators/harbor-resource-operator/ci.yaml: 
      reviewers:
  - fahricap
updateGraph: semver-mode
      With semver-mode the CSV needs no spec.replaces; OLM orders versions by semver.
    4. Commit with a DCO sign-off whose name and e-mail match the author (git commit -s), one operator version per pull request, and open the pull request against main.
    5. Their CI validates the bundle, installs it on Kubernetes and checks that the Deployment becomes healthy. Results are in the pull request's Checks tab; /retest reruns them. With the author listed in reviewers, a green run merges the pull request automatically. The listing appears on operatorhub.io after their release pipeline runs.
    6. Published versions are never edited; fixes go out as a new version.

    6. Upgrade test (from the second release on)¶

    operator-sdk run bundle the previous bundle image, create objects and wait for Ready, then operator-sdk run bundle-upgrade to the new one, and check that the objects stay Ready with their Harbor IDs kept. Add this to CI before claiming level 2 for a release that changes the CRDs.

    7. Submitting to OpenShift (community-operators-prod)¶

    Same bundle directory, pull request rules and reviewers, with two differences:

    • Tested on OpenShift. Their CI deploys the bundle on an OpenShift 4 cluster. Run it once on OpenShift Local (CRC) or OKD first: check that the pod is admitted under restricted-v2 (it sets no fixed UID), that the metrics Service works with OpenShift monitoring, and that the operator reaches a Harbor route with a cluster-signed CA.
    • File-based catalog (FBC). New operators are expected to use FBC. ci.yaml gets: 
      reviewers:
  - fahricap
fbc:
  enabled: true
  catalog_mapping:
    - template_name: semver.yaml
      catalogs_names: ["v4.16", "v4.17", "v4.18", "v4.19", "v4.20"]
      type: olm.semver
      Next to it go catalog-templates/semver.yaml and their FBC Makefile (make catalogs renders catalogs/v4.x/harbor-resource-operator/catalog.yaml with opm). Each release is two pull requests: the bundle, then the catalog update with the bundle pullspec their pipeline comments. Their auto-release option opens the second one automatically. Check the OpenShift versions currently served before writing catalogs_names, and add com.redhat.openshift.versions (for example "v4.16") to bundle/metadata/annotations.yaml in that copy.
